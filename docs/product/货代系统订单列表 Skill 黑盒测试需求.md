# 货代系统订单列表 Skill 黑盒测试需求 PRD

> 文档类型：黑盒测试需求 PRD
> 测试目的：验证 AI Skill 是否能够根据既定的货代后台 UI / UX / 交互规范，独立完成一个生产级列表页面
> 测试方式：**只将本 PRD 提供给 AI，不额外解释页面应该如何设计**

# 1. 需求背景

海运出口订单是货代公司最核心的业务对象。一个订单贯穿订舱、拖车、报关、装柜、提单、费用、文件、物流节点、异常处理到结算的完整流程。

业务人员每天需要在订单列表中完成：

* 查询订单
* 进入常用工作队列（待订舱、待报关、待补料等）
* 查看订单当前主流程状态
* 查看船期与截关时间
* 识别超期、异常、费用未确认、文件缺失等风险订单
* 查看详情
* 编辑订单
* 修改订单状态
* 分配操作员
* 标记异常
* 批量操作
* 导入 / 导出数据

与订舱委托列表相比，订单列表的业务复杂度明显更高：

* 主流程状态更多（18 个状态，存在分支与回退）
* 角色更多（操作、客服、单证、财务、主管、海外代理）
* 存在数据权限与字段权限
* 风险类型更多（超期、异常、费用、文件）
* 批量操作种类更多，且存在混合资格与部分失败

该列表是操作人员的主工作台，使用频率最高、停留时间最长，因此需要重点保证：

* 查询效率
* 信息密度
* 多状态并存下的可读性
* 风险识别效率
* 操作效率与操作安全
* 大数据量下的表格可用性
* 国际化适配
* 功能权限、数据权限、字段权限三层控制
* 不同屏幕尺寸下的可用性

# 2. 页面目标

本页面需要让业务人员能够快速完成以下任务：

1. 根据订单号 / 提单号 / 订舱号 / 箱号快速定位订单
2. 根据客户、港口、船公司、状态等条件筛选数据
3. 一键进入自己当前最关心的工作队列
4. 快速识别订单主流程状态
5. 快速识别超期、异常、费用未确认、文件缺失的订单
6. 查看开船、截关等关键时间节点
7. 快速查看订单概要并决定是否进入完整详情
8. 对订单执行状态修改、分配、标记异常等操作
9. 对多个订单执行批量操作，并清楚知道成功与失败情况
10. 导出当前查询结果、批量导入订单
11. 在大量数据中快速定位目标记录

* 标记异常

* 批量操作

* 查看列表（只能看自己客户的订单）
* 查询
* 查看详情
* 发送客户通知

* 上传文件
* 导出

* 编辑订单
* 修改订单状态
* 作废订单

---

## 3.3 单证人员

负责提单资料、补料、提单确认、文件确认。

权限：

* 查看列表
* 查询
* 查看详情
* 上传 / 确认文件
* 导出

无权限：

* 编辑订单核心字段
* 作废订单

## 3.4 财务人员

负责应收、应付、费用确认、开票、付款状态跟进。

权限：

* 查看列表
* 查询
* 查看详情
* 查看利润相关字段
* 费用相关操作
* 导出

无权限：

* 编辑订单
* 修改订单状态
* 作废订单

---

## 3.5 业务主管

负责订单监控、异常审批、数据审核、操作效率分析。

权限：

* 拥有操作人员全部权限
* 查看所属部门全部订单
* 作废订单
* 审批相关操作

---

## 3.6 海外代理

权限：

* 只能查看被授权的订单
* 只能维护海外段节点（到港、清关、派送、签收）
* 只能上传海外段文件

不可见：

* 内部利润
* 内部备注
* 内部操作日志

# 5. 订单状态

订单主流程状态包括：

```text
草稿
待订舱
订舱中
已放舱
待拖车
拖车中
待报关
报关中
已放行
待开船
已开船
运输中
已到港
清关中
派送中
已签收
已完成
已取消
```

状态流转规则：

1. 状态可以由业务节点自动推动，也可以由有权限用户手动修改。
2. 只允许沿主流程推进或显式回退，禁止跨级跳转。
3. 手动修改状态必须填写原因。
4. 取消订单必须二次确认。
5. 已完成订单默认只读。
6. 财务未结清订单不能归档。

合法流转矩阵：

```text
草稿 → 待订舱
待订舱 → 订舱中
订舱中 → 已放舱
已放舱 → 待拖车 / 待报关（服务项目决定分支）
待拖车 → 拖车中 → 待报关
待报关 → 报关中 → 已放行
已放行 → 待开船 → 已开船
已开船 → 运输中 → 已到港
已到港 → 清关中 → 派送中 → 已签收
已签收 / 已到港（无派送服务）→ 已完成
任意进行中状态 → 已取消（需二次确认并满足取消前置条件）
```

取消订单前置条件：

* 无已确认应收未冲销
* 无未关闭的高等级异常

不满足时必须给出具体阻断原因。

非法流转（跨级、逆向、已完成后再变更）必须被业务拒绝，并让操作者知道当前允许的下一步。

# 6. 风险与异常

## 6.1 风险提醒规则

系统需要自动识别以下风险订单：

1. 截关前 24 小时报关资料未齐
2. 截补料前 12 小时 SI 未提交
3. ETD 已过但订单未开船
4. ETA 已过但未到港
5. 已装柜但箱号封号缺失
6. 已开船但提单未确认
7. 应付费用大于应收费用
8. 高等级异常超过 24 小时未处理
9. 订单超过 7 天无任何更新
10. 必填文件缺失

要求业务人员能够在列表中快速识别命中风险的订单，并区分风险类型。

## 6.2 异常状态

订单异常状态包括：

```text
正常
异常
已处理
```

存在未关闭异常的订单需要持续可被识别，全部异常关闭后标记消除。

---

# 7. 文件状态与费用状态

## 7.1 文件状态

```text
完整
缺失
待确认
```

以下情况必须判定为文件缺失：

1. 已放舱但未上传 SO
2. 截关前 24 小时未上传报关资料
3. 已装柜但未上传装箱单
4. 已补料但无提单确认文件
5. 已产生费用但无供应商账单附件

## 7.2 费用状态

```text
未生成
待确认
已确认
```

财务角色重点关注费用状态；费用未确认是常用工作队列之一。

# 9. 查询行为

点击查询后：

* 使用当前所有查询条件进行查询
* 重置分页到第一页
* 保留当前查询条件

点击重置后：

* 清空查询条件
* 恢复默认查询状态
* 返回第一页
* 重新查询列表

刷新列表：

* 不应该清空当前查询条件
* 保留当前分页条件
* 重新获取最新数据

查询条件存在草稿态与已生效态之分：

* 修改查询条件但尚未执行查询时，不得触发表格刷新
* 业务人员应能区分哪些条件已生效、哪些只是草稿

业务人员需要能同时识别这些信息，且互不干扰。

单次查询可能返回：

```text
10,000+
```

条记录。

# 16. 行操作

每一行支持以下操作。

## 16.1 查看

点击后进入订单详情。

业务人员高频场景是先快速了解订单概要（当前状态、关键时间节点、风险、费用与文件概况、最近动态），再决定是否需要进入完整详情。快速了解概要的过程不应打断列表的查询与分页上下文。

---

## 16.2 编辑

已完成、已取消订单不可编辑。

财务已锁定的订单，不允许普通操作人员修改费用相关字段。

已开船订单修改关键字段（客户、起运港、目的港、ETD、截关时间）时，必须填写修改原因并留痕。

---

## 16.3 修改状态

* 只允许流转到合法目标状态（见第 5 章）
* 必须填写修改原因
* 非法流转必须被业务拒绝，并说明当前允许的下一步
* 流转后列表数据同步更新

---

## 16.4 分配操作员

将订单分配给操作人员，分配后操作人员收到待办。

---

## 16.5 标记异常

创建异常时需要填写：

* 异常类型
* 异常等级（低 / 中 / 高 / 严重）
* 异常描述
* 责任人
* 期望解决时间

标记异常后订单出现异常标记，责任人收到待办。

---

## 16.6 其他行操作

* 生成费用
* 上传文件
* 发送客户通知
* 查看日志
* 复制订单
* 作废订单

作废订单规则：

* 危险操作，必须二次确认，确认信息需说明影响范围
* 已开船、已完成订单不可作废

---

# 17. 批量操作

用户选择多条数据后，可以执行：

```text
批量分配操作员
批量修改状态
批量导出
批量生成费用
批量发送通知
批量标记异常
```

批量操作规则：

1. 不同状态、不同权限的数据可能不满足操作前置条件。例如：
   * 已完成订单不能修改状态
   * 已取消订单不能再次取消
   * 已开船订单不能作废
2. 选择的数据中既有满足条件又有不满足条件的（混合资格）时，执行前必须让操作者知道哪些将被跳过及原因，由操作者确认后继续。
3. 批量操作必须区分全部成功、部分失败、全部失败，并明确展示成功数量、失败数量与失败原因。
4. 部分失败时，失败的数据必须可识别、可再次处理，且失败明细可以下载。
5. 批量操作执行期间必须防止重复提交。

---

# 18. 导入导出

## 18.1 导出

支持导出：

* 当前筛选结果
* 选中的订单

导出内容：

* 当前查询条件
* 当前列表字段
* 当前查询结果

导出必须遵守数据权限与字段权限：无权限的订单与敏感字段不得出现在导出文件中。

如果数据量较大，需要采用异步导出机制，导出过程中需要能够体现：

```text
导出中
导出成功
导出失败
```

异步导出不能阻塞页面主要操作，完成后需要通知操作者。

## 18.2 批量导入

支持通过 Excel 批量导入订单基础信息，流程为：

```text
下载模板 → 上传文件 → 系统解析 → 数据预览 → 错误校验 → 确认导入 → 结果反馈
```

需要校验：

* 必填字段为空
* 日期格式错误
* 客户不存在
* 港口不存在
* 订单号重复
* 数据权限不足

导入结果必须明确展示：

* 总行数
* 成功行数
* 失败行数
* 每行失败的具体字段与原因

部分失败时，成功数据正常导入，失败明细可下载，修正后可以只重试失败部分。

# 19. 权限要求

权限分为三层。

## 19.1 功能权限

不同角色看到的功能不同（见第 3 章）。无权限的功能入口需要按照「隐藏」或「禁用并说明原因」两种策略之一处理，两种策略不得混用。

## 19.2 数据权限

* 普通操作员：只能看自己负责的订单
* 客服：只能看自己客户的订单
* 财务：只能看费用相关订单
* 主管：能看所属部门订单
* 海外代理：只能看被授权的订单

查询、导出、批量操作都必须遵守数据权限。

## 19.3 字段权限

敏感字段包括：

* 利润
* 毛利率
* 应收
* 应付
* 客户信用
* 内部备注
* 成本供应商

无权限的角色不应看到这些字段，而不是看到空白或占位值。海外代理不可见内部备注与内部操作日志。

# 21. 异常场景

页面必须考虑以下情况。

## 21.1 查询无数据

查询条件合法，但没有任何数据。需要与「系统本身没有订单数据」区分。

## 21.2 查询接口失败

列表接口请求失败，操作者可以重试，且当前查询条件不丢失。

## 21.3 网络异常

网络断开或者接口超时。

## 21.4 数据加载

首次进入页面需要显示加载状态，加载期间防止重复操作。

## 21.5 操作失败

例如：

```text
修改状态失败
分配操作员失败
导入失败
导出失败
```

失败后操作现场（已填内容、筛选条件、分页、选中数据）需要保留。

## 21.6 批量部分失败

批量操作中部分数据失败，失败数据可识别、可重试、明细可下载。

## 21.7 并发修改

A 用户打开订单，B 用户修改了该订单，A 用户再次操作时，系统需要能够识别数据已经发生变化，禁止静默覆盖。

## 21.8 权限不足

操作者访问了无权限的功能或数据时，需要有独立的表现形式，不得与网络错误混淆。

Skill 是否能够在**没有人工指定 UI 实现方案**的情况下，把业务需求转化为符合项目规范的生产级页面。

相比第一例（订舱委托列表），本例更关注：

* 复杂状态机下的业务正确性
* 多角色三层权限的完整性
* 批量与导入导出的部分失败处理
* 与第一例产出的一致性（系统级规范执行，而非单页偶然达标）

# 40. 最终验收结论

测试完成后，需要回答以下 5 个问题：

### ① Skill 能不能正确理解复杂业务？

18 个状态、分支流转、12 条风险规则、三层权限，如果理解失败，说明：

```text
需求理解能力不足
```

### ② Skill 能不能自主做出正确 UI 决策？

工作队列、查询方案、快速查看、批量反馈均未规定实现形式，如果决策失败，说明：

```text
设计规范不足
```

### ③ Skill 能不能把规范稳定转化为代码？

如果不能，说明：

```text
实现规范不足
```

### ④ Skill 能不能处理真实货代业务中的复杂状态？

混合资格、部分失败、并发修改、权限拒绝，如果不能，说明：

```text
业务场景规范不足
```

### ⑤ Skill 能不能稳定生成不同页面，而不是只做好一个页面？

这是最终测试重点。

需要继续使用不同业务 PRD 测试：

```text
订舱委托列表（已完成）
↓
海运出口订单列表（本用例）
↓
运单列表
↓
费用列表
↓
客户列表
↓
船期列表
↓
异常列表
```

如果不同业务列表最终仍然能够保持：

```text
统一布局
统一密度
统一交互
统一组件
统一状态表现
统一操作逻辑
统一国际化
统一权限
```

才能证明 Skill 真正具备「系统级 UI / UX 规范执行能力」，而不是只生成了一个看起来不错的页面。
